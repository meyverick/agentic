# OKF v0.2 — Documentation, Spotlight README & Progressive Wiki Reference

## A. OKF v0.2 Frontmatter & Provenance Contract

Required on all `wiki/*.md`, ADR, and specification files (`README.md` uses clean Markdown without raw YAML frontmatter so GitHub landing pages render cleanly for non-technical visitors):

```yaml
---
okf_version: "0.2"
type: WikiPage | ArchitectureDecisionRecord | Specification
title: <Human-Readable Title>
tier: beginner | practitioner | advanced | master
generated: { by: "<producer>/<version> | human:<id>", at: 2026-10-30T00:00:00Z }
sources: [{ id: <source-id>, resource: <url|path> }]
verified: { by: "human:<id>", at: 2026-10-30T00:00:00Z }
status: draft | stable | deprecated
stale_after: 2027-10-30
---
```

- **Provenance & Citations**: `generated: {by: <actor>, at: <ISO 8601>}` replaces legacy `timestamp`. Record `sources` list and attribute claims via `[^source-id]` footnotes (replaces `# Citations`).
- **Trust & Lifecycle**: `verified.by` -> `human:<id>` human-reviewed tier. `status`: `draft | stable | deprecated`. `stale_after`: `YYYY-MM-DD`.
- **Actor Convention**: `generated.by` / `verified.by` -> `<producer>/<version>` (agents) · `human:<id>` (people) · `process:<id>` (automation).
- **Reference Ingestion [CRITICAL]**: `./references/` present -> index via available knowledge-search tooling or inspect directly -> strictly READ-ONLY.

## B. Spotlight `README.md` Blueprint (Non-Technical)

Every repository (`./README.md` and `./modules/<package>/README.md`) must follow this structure (mandatory epigraph + 6 sections):

0. **Mandatory Epigraph**: line 1 is the verbatim blockquote mandated by `AGENTS.md` (`Mandatory README Epigraph`), then one blank line, then the `#` title.
1. **Headline & Elevator Pitch**: One sentence explaining what the project does in everyday human terms.
2. **Why It Matters (The Problem It Solves)**: Real-world analogy or everyday scenario showing the value before and after.
3. **Key Capabilities at a Glance**: 3–5 benefit-driven highlights (what it empowers people to do, not how the code works).
4. **Who Is This For?**: Clear explanation of how different people benefit from it.
5. **Explore the Documentation (Link to Wiki)**: Direct links to the local `./wiki/index.md` (and Public GitHub Wiki if public) for step-by-step guides, installation, and deep technical mastery.
6. **Support the Tools That Make This Possible**: One sentence naming the [thanks.dev](https://thanks.dev) support link, pointing to `CONTRIBUTING.md` for how to help and fund the project, and to root `DEPENDENCIES.md`, which lists every dependency with its upstream funding page. `DEPENDENCIES.md` and `.github/FUNDING.yml` are both generated by the `check` skill's `scripts/funding-gate.ts`; `CREDITS.md` is reserved for human contributors and is never generated.

* `[GOOD]` Spotlight `README.md`:
  > **Acme Sync** keeps your team's workspace organized automatically, making sure everyone always sees the latest version of a project without manual file juggling.
* `[BAD]` Technical `README.md` (Forbidden):
  > Run `cargo build --release` and set `DATABASE_URL=postgres://...` to initialize the Tokio MPSC worker channel.

## C. "Easy to Use, Hard to Master" `wiki/` Taxonomy

Every `wiki/` and `./modules/<package>/wiki/` directory must maintain:

- `index.md`: Master table of contents linking every page by difficulty tier (`Beginner -> Practitioner -> Advanced -> Master`).
- `01-getting-started.md`: Zero-assumed-context onboarding, installation, and first run.
- `02-guides-and-workflows.md`: Task-oriented tutorials and configuration patterns.
- `03-architecture-and-internals.md`: Deep dive into domain modules, state transitions, and schemas.
- `04-mastery-and-extension.md`: Performance tuning, edge-case diagnostics, security hardening, and plugin/extension contracts.
- `adr/`: Numbered Architecture Decision Records (`0001-record-name.md`).
